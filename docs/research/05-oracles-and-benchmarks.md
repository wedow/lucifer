# Tests, oracles and benchmarks

Research date: 2026-11-02. Recommendation: establish independent CPython, tier-differential, C-extension and concurrency oracles before tuning the optimizer; use AWFY as the Smalltalk comparison bridge, pyperformance and package workloads for Python breadth, and a human-controlled held-out set for generalization. These are proposed acceptance rules, not results from a working Lucifer. The fixed requirements remain full non-limited C-API support, an unmodified NumPy build passing its own suite, no GIL, and built-ins/stdlib mostly written in Python over native primitives (`README.md`).

No code from the vendored sources or the Smalltalk VM was built, installed or executed; no tests or benchmarks were run. Counts below come from host-Python source parsing and file enumeration. Evidence from the Smalltalk VM was read exclusively as source blobs and tree inventories at `origin/master`. `ST:<path>` below means a repository-relative path in the Smalltalk VM at that reference, not its working tree. URLs were read on the research date; unpinned web sources can change.

Minimal reproduction of the principal columns, from the Lucifer root; this reads source only:

```python
import ast
from pathlib import Path

for root in ("vendor/cpython/Lib/test", "vendor/numpy/numpy", "vendor/numpy"):
    files = sorted(Path(root).rglob("test*.py"))
    definitions = methods = 0
    for path in files:
        tree = ast.parse(path.read_bytes())
        parents = {child: node for node in ast.walk(tree)
                   for child in ast.iter_child_nodes(node)}
        for node in ast.walk(tree):
            if (isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef))
                    and node.name.startswith("test")):
                definitions += 1
                methods += isinstance(parents.get(node), ast.ClassDef)
    print(root, len(files), definitions, methods)
```

## 3. Correctness oracles

### 3.1 CPython 3.14: the independent oracle

Use the pinned 3.14.0 build as the primary differential reference and a separately labelled current-3.14 maintenance build for upstream bug-fix investigation. Do not silently update the semantic baseline because the host happens to be newer. Run identical source, inputs and dependency artifacts under CPython and every Lucifer tier; an independent interpreter matters because all Lucifer tiers may share the same erroneous Python builtin or primitive. Sources: `vendor/cpython/Lib/test/`, `Doc/reference/`, `Doc/library/`; the tier-common-mode risk follows directly from Lucifer's Python-over-primitives requirement (`README.md`).

Proposed comparison contract:

1. Record source/input hashes, argv, environment, locale, encoding, timezone, working directory, hash seed and RNG seeds. Use bounded subprocesses, private files/ports, fixed source filenames, captured stdout/stderr, exit status and signal. Replay the complete warm-up/mutation sequence in every arm; the Smalltalk VM's package pilot notes found unequal repetition histories misleading (notes described in §2; independent public verification is **unverified**).
2. For deterministic programs, compare output bytes exactly. Separately observe result types, values, alias relationships, mutations, exception class/arguments/chaining, warning categories and callback order. Serialize an explicit graph of supported test values with object IDs assigned by the harness; never compare process addresses or depend on pickle as the sole transport while testing pickle. For unordered values compare their specified semantics, retaining insertion order for dictionaries. Fix hash seed where possible; do not assume different implementations produce identical unspecified hash values.
3. Preserve signed zero, infinities and finite float values exactly for deterministic arithmetic; apply only operation-specific documented tolerances for libm/platform-sensitive results. State NaN comparison policy explicitly. Scrub only identified nondeterministic fields such as temporary root paths; broad exception/traceback or whitespace normalization can erase a defect. `vendor/cpython/Lib/test/test_math.py` and `test_math_property.py` provide numerical-oracle precedents.
4. For threads, compare invariants and allowed histories, not the exact stdout order from two different schedulers. Use barriers and explicit synchronization for deterministic cases. Test contractual atomic operations separately from compound read/modify/write programs that require application locks; CPython 3.14t is an additional concurrency reference, not a scheduling oracle (`vendor/cpython/Lib/test/test_free_threading/`; [free-threading HOWTO](https://docs.python.org/3.14/howto/free-threading-python.html)).
5. A discrepancy is a finding pending reduction/adjudication, not automatic proof CPython is correct in every implementation detail. Preserve the smallest standalone reproducer and all arm results; check the versioned documentation, upstream fix history and a second implementation where applicable. Crashes, timeouts, invalid observations and wrong answers remain separate dispositions (`ST:tools/difftest/run.sh`).

### 3.3 NumPy: the non-negotiable day-one acceptance lane

The principal static inventory is **186 files / 7,676 `test*` definitions** under `vendor/numpy/numpy`, not the whole repository's 213/7,872. Parametrization and generated dtype/shape cases mean actual collection can be much larger; its count is **unverified until a real environment collects the suite**. Include core, linalg, FFT, random, masked arrays, polynomial, f2py and test-support coverage; identify tools/typing/build-only checks separately. Evidence: the inventory above, `numpy/_core/tests/`, `numpy/f2py/tests/`, `numpy/typing/tests/`, `numpy/_pytesttester.py`, `pyproject.toml`.

Proposed artifact rule: run the same **unmodified NumPy extension binaries**, identified by wheel/build and `.so` hashes, under the selected compatible CPython oracle and Lucifer; preserve provenance of headers, compiler, BLAS/LAPACK and CPU features. Do not quietly rebuild NumPy against special Lucifer headers, disable assertions, remove difficult dtype cases or substitute a limited-API build. An import-only demo is insufficient. The exact initial artifact—ordinary `cp314` wheel/build, `cp314t`, or both—is an open ABI decision; the conservative proposal is an ordinary CPython 3.14 non-limited artifact for the compatibility claim plus a free-threading-aware artifact for its additional concurrency tests. Selecting only a `t` build must not silently narrow the owner's “unmodified build” requirement. [CPython extension HOWTO](https://docs.python.org/3.14/howto/free-threading-extensions.html) documents the differing build configurations; actual Lucifer interoperability is **unverified**.

Run NumPy's own suite in cold/default and deliberately warmed/deoptimized Lucifer configurations. Freeze its upstream collection/outcome manifest against CPython; require every supported-platform case to pass with the same justified upstream skips, no Lucifer-only skips or new xfails. Include optional property-test dependencies: this checkout's `pyproject.toml` explicitly permits skipping property tests when Hypothesis is absent. Missing Hypothesis must therefore be visible, not a convenient route to the public acceptance claim. f2py requires a recorded compiler environment; absence is a coverage gap, not evidence of C-API compatibility.

Add focused full-API probes for borrowed/new/stolen references, refcount macros and visible layouts, type slots/subclassing, buffer leases and strided views, C-created cycles, capsules, vectorcall, callbacks, native threads and finalizer reentrancy. Test a reference held only by C across a Lucifer collection/deopt, and a Python object materialized for C then mutated by either side. NumPy supplies important real coverage, but passing it alone cannot establish every public C-API function or arbitrary third-party thread safety (`vendor/cpython/Modules/_testcapi/`; `vendor/numpy/numpy/_core/tests/`).

Concurrency evidence should include `numpy/_core/tests/test_multithreading.py` and `numpy/testing/_private/utils.py:run_threaded`. The former is marked `thread_unsafe` **because it already creates threads**; filtering that mark out would lose the explicit thread tests. `numpy/conftest.py` also marks f2py tests thread-unsafe. Use a serial outer runner for such modules, while still executing their internal concurrency. Verify any `NOGIL_BUILD`-guarded paths actually run: NumPy derives this flag from `sysconfig.get_config_var("Py_GIL_DISABLED")`, not from observed parallelism.

### 3.5 Hypothesis differential fuzzing

Use a CPython-hosted Hypothesis driver to generate bounded programs/operation traces, launch the four oracle arms and shrink divergences. This avoids needing Hypothesis and its dependencies inside the first Lucifer executable. Add a Lucifer-hosted Hypothesis suite later to test that ecosystem dependency too. Rule-based state machines generate operation sequences and reuse values, which fits mutable built-ins and aliasing. [Hypothesis stateful documentation](https://hypothesis.readthedocs.io/en/latest/stateful.html); an existing numerical-property precedent is `vendor/cpython/Lib/test/test_math_property.py`.

| Target | Generated cases and observable consequences |
|---|---|
| Numbers | Huge integers, sign/shift/division/modulo boundaries, bool/int interactions, int/float comparisons around precision boundaries, signed zero/NaN/infinity, `__index__`, reflected operators and overflow-to-bigint transitions |
| Lists/tuples/ranges/slices | Negative/huge indices, zero slice steps, extended slices, self-assignment, iteration during mutation, callback-triggered mutation, subclass overrides, alias-preserving copies |
| Dicts/sets | Colliding hashes, raising/reentrant `__hash__` and `__eq__`, equal-but-distinct keys, deletion/reinsertion order, iterator invalidation, storage transitions and references retained across resize |
| Strings/bytes/buffers | Surrogates, non-BMP characters, encoding error policies, zero bytes, bounds, memoryview format/shape/stride/release, exported buffers during mutation |
| Object model/control | Descriptor precedence, `__getattribute__`, metaclasses/MRO, monkeypatching after warm-up, closures, generators/send/throw/close, `try/finally`, exception chaining, async cancellation and context propagation |
| Extension seams | Python callbacks from C, type slot changes, buffer owners, borrowed references, release/reattach thread state, C-owned references during GC and deopt |

Warm with stable types, then introduce rare types, overflow, empty containers and overrides; otherwise a random test can finish before compilation. Cross product sampled seeds with worker counts, GC pressure and forced-deopt schedules. Record the actual generated source/trace and minimized failure; a random seed alone does not survive generator-version changes. Timeouts, generator rejection and failure to reach the target tier are distinct from semantic agreement. These controls are proposed extensions of `ST:tools/difftest/run.sh` and `templates.sh`, not a claim of complete state-space exploration.

### 3.6 Free-threading tests

`vendor/free-threaded-compatibility/README.md` describes ecosystem coordination; its `docs/testing.md`, `thread_sanitizer.md`, `porting-extensions.md` and `tracking.md` supply testing practice and package status, not a single suite to “pass.” Start with CPython's 22 free-threading test files, its ordinary threading/concurrent-futures/queue suites and NumPy's explicit multithreaded tests. Include runtime/native ThreadSanitizer jobs where the eventual implementation permits useful instrumentation; sanitizer silence is supporting evidence, not a proof for uninstrumented assembly/JIT code (`docs/thread_sanitizer.md`).

Use [pytest-run-parallel](https://github.com/Quansight-Labs/pytest-run-parallel) for repeated instances of **the same test** in a shared-process thread pool, e.g. a proposed job with `--parallel-threads=8 --iterations=20`. It shares fixtures, with special handling for directly requested temporary-path fixtures, and detects/marks some unsafe tests. It is a race-stress tool, not a test-suite accelerator. Preserve its single-thread-only dispositions separately. Do not equate process-based pytest-xdist success with shared-heap safety.

Write additional deliberate shared-object tests: simultaneous container resize/read; publication of functions/classes and inline-cache invalidation; C-extension callbacks from external threads; weakrefs/finalizers during concurrent collection; thread-local/contextvar isolation; exception state; lock ordering; cancellation; fairness and blocking I/O. Separate harness global-state races from application/runtime races. Compare synchronized results and valid histories to CPython 3.14t, with repeated seeds and barriers. The guide explicitly warns that concurrent independent test instances cannot discover every unsafe shared use of a library-defined data structure (`vendor/free-threaded-compatibility/docs/testing.md`).

For each no-GIL job, record build capability **and runtime state after imports**, including in child processes. CPython may re-enable the GIL for an unmarked extension; forcing it off on CPython is a deliberate adversarial configuration, not proof the extension is safe. Lucifer has no GIL fallback: record unsafe-extension findings and the supported call contract rather than calling serialized execution a no-GIL pass. Full API availability and third-party shared-state correctness are distinct test obligations. [CPython free-threading HOWTO](https://docs.python.org/3.14/howto/free-threading-python.html), [extension HOWTO](https://docs.python.org/3.14/howto/free-threading-extensions.html).

| CPython 3.14.0, JIT on | Same-source JIT comparison | `--enable-experimental-jit=yes` or `yes-off`, then `PYTHON_JIT=1`; record availability/enabled state via `sys._jit` outside timed loops. Setting the variable on a build without JIT support is not a JIT-on measurement (`Doc/using/configure.rst`, `Doc/using/cmdline.rst`, `Lib/test/test_sys.py`). |
| CPython 3.14.0t | Main no-GIL comparison and concurrency reference | `--disable-gil`, `PYTHON_GIL=0`/`-X gil=0`, capability and `sys._is_gil_enabled()` checks after imports. A labelled GIL-enabled run of the same `t` binary can isolate some configuration effects. **This pinned release rejects JIT + free threading** in `vendor/cpython/configure.ac:2792`; no fictional 3.14.0t+JIT cell. |
| PyPy Python 3 | Mature optimizing-JIT comparison | Pin a published Python 3 build, release, language version and extension artifacts. [v8.0.0 release notes](https://doc.pypy.org/release-v8.0.0.html) distinguish 3.11 and 3.12 beta; [release archive](https://downloads.python.org/pypy/) lists v8.0.1 artifacts. The local `vendor/pypy3` source targets 3.12.15 / PyPy 8.0.2 alpha and is not itself a measured executable. Shared-version workload subset only for common summaries. |
| GraalPy | Independent optimizing JIT and C-extension integration comparison | Pin distribution/edition, language level, VM/JDK configuration, warm-up and package provenance. [Repository README](https://github.com/oracle/graalpython/blob/master/README.md) currently describes Python 3.13; [published release listings](https://github.com/oracle/graalpython/releases/) also contain Python 3.12 builds. These are different references, not proof of 3.14 support. Its [implementation documentation](https://github.com/oracle/graalpython/blob/master/docs/contributor/IMPLEMENTATION_DETAILS.md) describes a GIL, so treat shared-heap thread scaling as a measured control, not another no-GIL implementation. |
| Lucifer interpreter / template / SSA | Tier correctness and speed attribution | Same production Python built-ins and primitive contract; record actual tier reachability, JIT work, deopt activity and GC. Support forced tiers only as explicit runtime/test configurations; no special-case benchmark implementations (`README.md`; donor `tools/difftest/run.sh`). |
| Smalltalk/Go/Java bridge | AWFY context, optional HTTP controls | Existing time ratios are historical. New comparisons require a later authorized measurement with matching workload and host; no language-wide score from AWFY alone. |

For each dataset, preserve machine/CPU topology, kernel/microcode, memory, affinity/governor, background load, runtime binary hash/build flags, source/input/dependency hashes, process and application-thread counts, RNG/hash seeds, warm-up/measurement plan and every raw sample. Use monotonic elapsed time; independent fresh launches, paired/interleaved baseline/candidate order and baseline/baseline controls. Keep cold wall time, time-to-first-answer, compilation/warm-up cost, steady throughput, peak/resident memory and sustained GC behavior separate. The donor's evidence files and `ST:tools/perf/{gate,icount,status-startup,warmup}.sh` supply concrete precedents; its one-process AWFY intervals have the limitation recorded in §2.

Compute time ratios as `T_Lucifer/T_reference` and state the direction. Use geometric means only over a predeclared identical set of correct applicable rows, accompanied by per-row results, worst regressions and coverage `measured/expected`. Pairwise-common subsets are useful diagnostics but not interchangeable public “overall” scores when each runtime gets a different denominator. Missing/failed/never-steady rows remain visible; never impute them as 1.0 or quietly delete them. Keep AWFY, Python-core, extension-heavy, startup, HTTP and scaling summaries separate. These are recommended reporting rules, motivated by the explicit partial/reference/fallback accounting in `ST:vm/results/all-runtimes-2026-11-01/README.md` and `status-2026-11-01/README.md`.

## 7. Held-out set: a real separation of access and feedback

Proposed ownership: a human reviewer or separate evaluator controls an external repository/artifact store that builders and their tools cannot read. A directory committed inside Lucifer, or a public benchmark merely labelled unseen, does not establish this boundary. Existing public AWFY/pyperformance/package suites are development evidence; conceal new workload selection, input distributions and combinations, not a promise that publicly known source can be erased from a builder's prior knowledge. This closes the gap identified in the donor scan (§2).

Proposed operating protocol:

1. Before optimizer tuning, evaluator seals the manifest, dependency/runtime versions, source/input hashes, correctness answers, run protocol, category weights and missing-row rules. Start with approximately **20–30 independent workload families**, spanning built-in-heavy Python, object/graph code, parsing/templates, extension callbacks, thread scaling and sustained services. This is a planning quantity, not an empirically sufficient sample-size claim. Categories may be public; selected cases and fresh inputs remain private.
2. Keep a public development set, a limited-feedback evaluator validation set and a final sealed release set. Split by algorithm/package lineage and operation mix, not random files or alternative input sizes of the same program. Deduplicate AWFY/pyperformance overlaps such as Richards/DeltaBlue/NBody; a renamed port is not independent validation.
3. Freeze and hash candidate and baseline binaries before submission. The evaluator runs both against unchanged artifacts and checks correctness first. Run fresh launches and noise controls on the same hardware. Cap submissions per milestone and report scheduled summaries/category regressions plus the number of attempts; immediate per-case tuning feedback would turn the set into training data.
4. A correctness failure is reduced and disclosed promptly. Once builders see a case or detailed performance profile, move that family into the public regression set and replace its held-out slot before the next evaluation cycle. Do not retain a known failure in secret to protect a performance experiment.
5. Preserve evaluation history, including failed submissions and denominator changes. After the release decision, disclose enough source/input/protocol to reproduce published claims, retire those cases from the secret pool and replenish with genuinely fresh families/inputs. Hold-out evaluation is a check for overfitting, not a substitute for the public full-suite gates.

Human supervision is already part of this research's review model; this protocol is a recommendation, not a claim a secret evaluator or access boundary currently exists. Selection, artifact storage and final submission limits remain open decisions.

## 8. Ordering, acceptance and open decisions

“Day one” means the first engineering acceptance contract: the complete required manifest is present even when early implementation is red. It does **not** mean declaring partial NumPy or limited-API support acceptable until later. The fixed public bar in `README.md` is met only when the unmodified NumPy build's full applicable suite passes while Lucifer remains GIL-free.

| Stage | Establish/run | Evidence required to advance |
|---|---|---|
| **Day one: oracle and artifact foundation** | Pin CPython 3.14.0, its tests, NumPy artifact/test/dependency manifest and initial runtime matrix; binary-level semantic smoke; CPython/interpreter/template/SSA differential runner; full C-API fixture lane; NumPy full-suite acceptance job; CPython free-threading and explicit NumPy thread tests; small Hypothesis host driver; AWFY manifest and all 100 pyperformance selectors with honest readiness statuses; first public package suites; sealed-set ownership. | Crash/hang/wrong-answer/invalid distinctions, nonvacuous collection and tier coverage, named exclusions, stored reproducers, no-GIL state checks. Initial red results are recorded; no compatibility milestone is awarded before the fixed requirements pass. |
| **Alongside the first optimizing tier** | Guard/OSR/deopt/GC stress, rare-type phase changes, Python built-in storage changes, callbacks/native roots, concurrent publication; fast instruction panel; nightly cold/warm package and NumPy shards; initial 15-probe scaling panel and fixed-work thread kernels; portable HTTP tiers; startup/memory measurements. | Optimizer changes reproduce identical semantics across independent oracle and all Lucifer tiers, including Python built-ins. Real thread overlap/scaling, no hidden GIL reenablement, and preserved native-artifact hashes. These checks develop with the tier, not after performance stabilization. |
| **Broader daily train** | Every applicable pyperformance entry, 20 package suites, published runtime comparisons, explicit accelerated stacks, application-derived workloads, full concurrency matrix, dependency/resource-complete NumPy runs. Use fast per-change checks, broader correctness/count jobs and isolated periodic timing, following the donor's current process split. | Raw data, stable expected-row matrix, noise-qualified per-row regressions and coverage; separate summary families. Reference updates are visible. |
| **Later breadth and scale** | Large multi-socket/NUMA machines; sustained overload/fault tests; expensive sanitizers/instrumentation; real DB TechEmpower workloads; wider PyPI corpus; snapshot/restart tests if selected; rotating sealed release evaluations. | No extrapolation of six-core scaling to many-core hardware; no silent weakening of compatibility to obtain a timing score. Full day-one C-API/NumPy/no-GIL obligations remain in force. |

Recommended first benchmark panel: canonical 14 AWFY rows; a modest predeclared pyperformance subset spanning builtin/string/numeric/object/generator/async/serialization/startup/application behavior; all 15 CPython micro-scaling probes plus one fixed-work CPU and one queue/allocator workload; and portable plaintext/JSON/template HTTP. Keep NumPy correctness mandatory from the outset, while measuring native-kernel speed separately from Python JIT speed. This combines the donor's verified-work/tier methodology with the Python mechanisms AWFY omits (§§2, 5).

Open decisions for implementation planning, with uncertainty preserved:

| Decision | Recommendation / unresolved evidence |
|---|---|
| **Which unmodified NumPy binary/ABI is the initial public artifact?** | Identify a concrete ordinary CPython 3.14 non-limited artifact and its hashes, with a separate `t` artifact for applicable free-threading coverage. The chosen release's complete dependency/toolchain/BLAS/Fortran/property-test collection is unverified; source-tree counts cannot answer it. Do not choose a narrower artifact definition implicitly. |
| **Which CPython-specific assertions are required?** | Audit the full-API and Python-visible parts of every category, including `cpython_only`; retain a reviewed per-node manifest. The 404 directly decorated declarations are a starting index, not an exemption list. |
| **What concurrency contract and observability does Lucifer expose?** | Exercise ordinary Python threading/C thread-state APIs first; specify container guarantees, native callbacks, context defaults and lightweight-task API mapping. Use 3.14t as evidence while checking documented semantics. Tests cannot make a third-party library's unsynchronized internal global state safe by declaration. |
| **Which pyperformance metadata/dependency environment is authoritative?** | Resolve xDSL's 0.46.0/0.54.3 conflict and SQLGlot spelling, lock transitive dependencies, and inventory emitted names/backends. Explicitly retire `2to3` from target-compatible summaries; optional revived legacy rows get new provenance. No installations were performed to verify readiness. |
| **Which PyPy/GraalPy builds and common-language subsets?** | Pin published binaries and advertised language versions independently of local source branch names. Preserve unsupported 3.14 syntax/dependency rows; compare the common subset without weakening Lucifer's 3.14 correctness target (§6). |
| **What constitutes a perf regression?** | Calibrate independent-process and base/base noise before choosing row/suite thresholds and budgets. Keep time, instructions, warm-up, memory and scaling separately accountable. A speed win cannot outweigh a required wrong answer. |
| **How is held-out access enforced?** | Name the human evaluator, artifact location, submission limits and disclosure/rotation policy before optimizing against public scores. No such mechanism was verified in either project during this research. |

The main research result is an executable acceptance design, not a performance forecast: independent semantics, full native compatibility and real shared-heap concurrency need overlapping tests; no single suite substitutes for the others. The inspected counts and source gaps define the initial inventory, while actual collection, runtime support and speed remain explicitly unverified.
