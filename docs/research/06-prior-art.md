# Fast Python prior art: what worked, what stopped, and what Lucifer inherits

Research date: **2026-11-02**. Design input for human review; no implementations, builds, installations, or benchmarks were run. The fixed requirements are those in [`README.md`](../../README.md): full non-limited C API from day one, NumPy's own suite against an unmodified NumPy build, no GIL, and predominantly Python standard-library and built-in implementations compiled over native primitives. Recommendations below retain all three requirements.

## Reading the evidence

The durable result is that fast Python execution is achievable, but execution speed alone has repeatedly failed to deliver a deployable replacement. PyPy demonstrates long-lived meta-tracing; Pyston and Cinder demonstrate the value of retaining CPython compatibility; Unladen Swallow, Pyston v1, and Skybison document failures to turn compiler progress into enough compatible production deployment. These are different outcomes, not evidence that every alternative implementation died. Sources and narrower qualifications follow in the individual records.

**Scope.** All requested projects are covered separately, including Pyston's two architectures and Static Python within the Cinder family. Additional records cover Skybison, HotPy, Shed Skin, Cython, Numba, mypyc, Stackless, and PyPy-STM because they test important parts of Lucifer's premise. This is a survey of substantial documented approaches, not a claim to enumerate every abandoned repository. Absence of a published result or post-mortem is reported as **unverified**, not converted into a speed estimate or an invented cause of death.

**Compatibility has four separate meanings.** Language compatibility does not imply C-source compatibility; rebuilding an unchanged extension source does not imply loading a pre-existing CPython wheel; importing NumPy does not imply passing NumPy's suite. A NumPy implementation or a bridge into a second CPython interpreter is another category again. The non-limited API exposes object layouts and inline operations: `vendor/cpython/Include/cpython/listobject.h` defines `ob_item`, direct `PyList_GET_ITEM`, and direct `PyList_SET_ITEM`; `vendor/cpython/Include/object.h` describes address stability and reference ownership. Lucifer's Python implementation of a list algorithm therefore still needs a faithful native storage and C-facing contract.

**Benchmark rule.** Speedup means `CPython elapsed time / candidate elapsed time`; 1.65× means 65% more throughput for the measured work, not 65% less time. Historical `perf.py`, PyPy's own suite, application throughput, numeric kernels, and projected speedups are identified separately from **pyperformance**. Results from different machines, Python releases, warm-up policies, and subsets are not a common leaderboard. `vendor/pyperformance/README.rst` explicitly warns that the suite is not tuned for PyPy. No missing benchmark was run to fill a table.

**People and dates.** A named founder, paper author, lifetime contributor, and paid full-time engineer are not interchangeable. Counts below identify which was actually verified; exact concurrent staffing/person-years are **unverified** where primary sources do not disclose them. Release dates establish activity, not continuous funding.

**Local evidence.** Read-only revisions inspected: PyPy `vendor/pypy3`, branch `py3.12`, commit `2e890abd7377b8dc1f5e94064e91c9bbfd8ddcf0` (Python **3.12.15**, PyPy **8.0.2 alpha**, `pypy/module/sys/version.py`); CPython `ebf955df7a89ed0c7968f79faec1de49f61ed7cb`; NumPy `df9913aa4ea20c33728fbc434acc66c3285f12a2`. Counts from `rg --files`: PyPy's `pypy/module/cpyext/` has **283 files**, including **93** under `test/`; `pypy/objspace/std/` has **108 files**. A textual count of lines matching `^def test_` or `^    def test_` in cpyext test Python files gives **736 definitions**, not 736 executed/passing tests. The copyright-holder block in `vendor/pypy3/LICENSE` has **437 entries**, including organizations; it is explicitly not a team-size estimate.

## PyPy: a successful JIT, an expensive foreign object model

| Dimension | Evidence |
|---|---|
| Approach | An RPython interpreter and object space translated to native code; a **meta-tracing JIT** traces execution of that interpreter, with guards and recovery, rather than compiling Python methods independently. Built-ins largely live in RPython, which is a restricted, statically translatable language, not arbitrary Python running over a tiny primitive layer. See `vendor/pypy3/pypy/doc/architecture.rst` and [`architecture`](https://doc.pypy.org/architecture.html). |
| C API / ecosystem | **cpyext** emulates the documented CPython API, object representations, and ownership. Many extensions work after rebuilding; there are documented differences involving tuples, type slots, and implementation details. Pure-Python Django/Twisted and scientific packages are explicitly supported use cases. See `vendor/pypy3/pypy/doc/cpython_differences.rst` and [compatibility](https://pypy.org/compat.html). |
| NumPy | The local FAQ says upstream NumPy passes its suite through cpyext. This is a project statement, not a fresh run or proof that an arbitrary CPython NumPy wheel loads. The separately reimplemented **numpypy/micronumpy** reached about **80% parity**, then was discontinued in favor of upstream compatibility: `vendor/pypy3/pypy/doc/faq.rst:188–226`. |
| pyperformance | A verified individual result: v7.3.22's `_pickle` implementation reduced the pyperformance `pickle` runtime from **5.7× to 1.6× CPython's time**, contingent on the benchmark using `_pickle`. The release does not identify the exact CPython build for that number. A comparable complete-suite summary is **unverified**. [Release and benchmark-selection caveat](https://doc.pypy.org/release-v7.3.22.html). |
| Other speed evidence | PyPy's June 2026 infrastructure report gives **3×** on its old runner and **4.3×** on the new runner against CPython, with changed hardware/compiler/baseline. These are its own benchmark-suite results, not a controlled release-to-release improvement or a pyperformance summary. [Runner report](https://pypy.org/posts/2026/06/benchmarker2-for-pypy.html). |
| People / years / status | Began **2003**; active through the **8.0.1 release in October 2026**. Founders/core developers are named in the [team history](https://pypy.org/people.html); present FTE count is **unverified**. Current releases include 3.12 beta and 3.11, still behind CPython 3.15. [8.0.1 notes](https://doc.pypy.org/release-v8.0.1.html). |

**What worked.** High-level interpreter implementation, object/storage specialization, allocation elimination, and cross-call tracing produce substantial pure-Python gains. PyPy also persisted long enough to make upstream NumPy useful. Its architecture is evidence for expressing runtime semantics at a high level; it does not establish that RPython's translation restrictions can be removed at no cost. Sources: architecture above; `vendor/pypy3/pypy/objspace/std/`; [`list strategies`](https://doc.pypy.org/list-strategies.html).

**What constrained it.** The cpyext account identifies stable C pointers versus moving managed objects, refcount emulation, conversions, and borrowed references. In its concrete example, borrowing a list element forces an integer-storage list into boxed `PyObject*` storage, losing the strategy's benefit for subsequent Python execution. Some call microbenchmarks improved dramatically after **2–3 person-months** of focused work, yet mixed real applications remained expensive in that 2018 account. This is a dated mechanism report, not a claim that every 2026 call has the old cost. [Cuni's cpyext analysis](https://pypy.org/posts/2018/09/inside-cpyext-why-emulating-cpython-c-8083064623681286567.html); local implementation: `pypy/module/cpyext/pyobject.py` and `pypy/doc/discussion/rawrefcount.rst` under `vendor/pypy3/`.

**A consequential 2026 change.** PyPy 8 hides its extra managed-object link in a prefix to make the limited CPython 3.12 ABI usable; the release says wheel/import-tool integration is still missing. The local `py3.12` standalone target enables this prefix layout (`vendor/pypy3/pypy/goal/targetpypystandalone.py:368–370`); visible `PyObject` has the two CPython fields, while prefix-less static/foreign objects use separate mappings (`pypy/module/cpyext/parse/cpyext_object.h:6–19`, `pypy/module/cpyext/pyobject.py:112–128,414–449`, under `vendor/pypy3`). This source is newer than the release account; end-to-end wheel/tool integration at this revision is **unverified**. The release also drops the default HPy backend because HPy did not gain enough support to become a standard; `_hpy_universal` and library support remain in the source but are disabled in the standard module configuration (`vendor/pypy3/pypy/config/pypyoption.py`). Neither change is proof of full non-limited binary compatibility. The lesson for Lucifer is to make existing extensions work without depending on ecosystem migration to a friendlier API. [8.0.0 design/release notes](https://doc.pypy.org/release-v8.0.0.html).

**Parallelism remains separate.** Mainline PyPy has a GIL. Its FAQ explicitly separates making GC thread-safe from reviewing mutation semantics throughout every built-in. Its abandoned STM variant is discussed below; the successful JIT did not by itself solve parallel Python. Source: `vendor/pypy3/pypy/doc/faq.rst:160–185`.

## GraalPy: partial evaluation works; native compatibility is still a product

**Approach and reach.** A self-optimizing Truffle interpreter, principally Java/Python, is partially evaluated by Graal into optimized native code. This is interpreter specialization/partial-evaluation JIT compilation, not PyPy's meta-tracing. Oracle's implementation account describes the architecture. Native extensions use a C-API compatibility layer: source compatibility rather than general CPython ABI compatibility; GraalPy-specific builds, wheels, and pip-applied patches matter. Native execution replaced the earlier LLVM-bitcode default. NumPy and PyTorch work for many uses, but an unmodified NumPy build passing its entire suite is **unverified**. [Architecture](https://medium.com/graalvm/how-to-contribute-to-graalpython-7fd304fe8bb9), [native extension policy](https://www.graalvm.org/jdk24/reference-manual/python/Native-Extensions/), [native-mode transition](https://docs.oracle.com/en/graalvm/jdk/20/docs/release-notes/).

**Numbers and people.** The current README claims about **4× pyperformance geometric-mean speedup**. Its exact baseline release, hardware, exclusions, warm-up settings, and raw comparison are **unverified** here. It separately reports roughly **85% of CPython tests**, successful installation of recent versions of **93% of 600 packages**, and **over 65% of combined package tests** passing. Installation is a substantially weaker test than correctness. Active since at least **2017**, when Tim Felgentreff dates his Oracle/GraalPy leadership; exact team FTE is **unverified**. [Maintainer metrics/current status](https://github.com/oracle/graalpython), [leader's chronology](https://www.timfelgentreff.de/).

**Outcome.** Active, not abandoned. Shared compiler infrastructure and partial evaluation delivered speed without hand-writing a Python optimizer from scratch. The documented costs are warm-up and mode-dependent native crossings; broad extension compatibility remains experimental. These constrain adoption, not proof of a terminal failure. [Versioned performance FAQ](https://docs.oracle.com/en/graalvm/jdk/20/docs/reference-manual/python/FAQ/).

## Pyston v1: LLVM could not compensate for compatibility and memory

**Approach and reach.** A new Python 2.7 runtime, **2014–2017**, with LLVM optimizing compilation, later a baseline JIT, and an initial tracing collector replaced by reference counting. The v0.5 announcement reports **unmodified NumPy 1.11's whole suite with one failure**, whose fix was accepted upstream; NumPy trunk had three. Its Cython build chain was modified, and NumPy's suite ran around **2× slower than CPython**. Thus this is unusually strong compatibility evidence, but not an exact match for Lucifer's unchanged-build/zero-failure bar. Switching to reference counting cost about **10% against v0.4** while fixing object-lifetime compatibility. [History](https://github.com/pyston/pyston#history), [v0.5 evidence](https://blog.pyston.org/2016/05/25/pyston-0-5-released/).

**Numbers and people.** v0.6.1 reported **1.95× on its standard benchmarks**, **1.48× on its web suite**, but only **1.10× on Dropbox's server**. The first number's equivalence to modern pyperformance is **unverified**. Kevin Modzelewski and Marius Wachtler were the two developers transitioning off the project; v0.6 also identifies Nexedi's Boxiang Sun and other contributors. Exact concurrent staffing is **unverified**. [Final sponsored release](https://blog.pyston.org/2017/01/31/pyston-0-6-1-released-and-future-plans/), [contributors](https://blog.pyston.org/2016/11/11/pyston-0-6-released/).

**Why sponsorship ended.** Modzelewski's post-mortem says compatibility and memory consumed much more work than expected, while Dropbox increasingly used Go for performance-sensitive components. Real software depended on destruction timing, frame inspection, function mutation, and rich override behavior. Requests per second per GB mattered more than isolated speed. He explicitly rejects the original idea that attaching LLVM would make the hard problems disappear. This explains a sponsor's decision, not the impossibility of a new runtime. [Personal retrospective](https://blog.kevmod.com/2017/02/01/personal-thoughts-about-pystons-outcome/).

## Pyston v2: keeping CPython worked; shipping a fork still hurt

**Approach and reach.** Work restarted in **2019**, with a CPython-3.8-derived release in **2020**: quickening, caches, build/interpreter optimization, and a low-overhead DynASM JIT instead of v1's greenfield LLVM runtime. Full Pyston preserved the API but changed the ABI, requiring rebuilt extensions. **Pyston-lite** packaged the JIT as an extension using normal CPython packages. NumPy-specific complete-suite passage for v2 is **unverified**; v1's result cannot establish it. [Implementation/history and package rules](https://github.com/pyston/pyston).

The team's September 2022 measurements on an **EC2 c6i.xlarge**, relative to **CPython 3.8**, are directly labeled pyperformance. Baseline patch release, suite revision, and exclusions are **unverified**. [Measurement and strategy announcement](https://blog.pyston.org/2022/09/29/announcing-3-7-3-10-support-and-a-new-direction/):

| Candidate | pyperformance speedup | Project macrobenchmark speedup |
|---|---:|---:|
| Full Pyston 2.3.5 | **1.65×** | **1.28×** |
| Pyston-lite 2.3.5 / Python 3.8 | **1.28×** | **1.10×** |
| CPython 3.11rc2, same comparison | **1.26×** | **1.12×** |

**People and outcome.** Modzelewski and Wachtler joined Anaconda in 2021, then left in 2022 and reduced their investment. Maintaining the full fork across four Python versions was impractical; rebuilding/installing packages impeded adoption. Lite had roughly **100× the daily downloads**, qualified by substantial CI traffic. The current repository explicitly says **no longer maintained**; the last full release is [2.3.5, September 2022](https://github.com/pyston/pyston/releases/tag/pyston_2.3.5). Exact staffing beyond the two principals is **unverified**. The failed part was sustaining a separately distributed runtime; a smaller integration surface delivered more use despite less speed.

## Cinder / CinderX: production method JIT, progressively smaller fork

**Approach.** Meta's Cinder combined CPython quickening, frame/coroutine work, immortal objects, and a **function-at-a-time SSA JIT**: bytecode → CFG/HIR → SSA → LIR → native code, with guards, inlining, and deoptimization. It accelerated Instagram's production Django service. Carl Meyer dates its beginning to **2017 or 2018**, explicitly uncertain. [Author-written architecture](https://engineering.fb.com/2022/05/02/open-source/cinder-jits-instagram/), [firsthand chronology, 04:24 onward](https://talkpython.fm/episodes/show/369/getting-lazy-with-python-imports-and-pep-690).

**C API and NumPy.** Retaining CPython's objects/runtime avoids a foreign-object emulation layer. CinderX turned the optimizations into an extension to reduce Python-version maintenance; 3.10–3.12 still required fork patches, whereas **3.14 is the first supported stock CPython**. NumPy compatibility through that host is a reasonable **inference**, not a verified full-suite JIT result. Some runtime features, including parallel GC and lighter frames, remain incompatible with stock CPython. Parallel GC does not establish GIL-free Python execution. [Current CinderX design/status](https://github.com/facebookincubator/cinderx).

**Numbers and people.** A public primary-source **pyperformance summary is unverified** after examining the repository and performance docs. The official x64 Broadwell microbenchmarks include dynamic-JIT **Richards 3.73s → 2.12s** and **Fannkuch 4.24s → 4.40s**: both gains and regressions exist. They are not pyperformance. The Static Python paper acknowledges **15 combined Cinder-JIT/Static-Python developers**, not 15 concurrent FTE; exact staffing is **unverified**. [Measurements](https://facebookincubator.github.io/cinderx/), [acknowledgments, pp. 24–25](https://lukuangchen.github.io/Downloads/Programming-2023_StaticPY.pdf).

**Outcome.** Active, production-used at Meta, experimental externally, with weekly releases. The fork's evolution into CinderX is an explicit response to porting costs, not abandonment. Its success supports a low-overhead baseline and guarded method optimization; its distribution history warns that keeping up with CPython is part of the runtime's permanent cost.

## Static Python: stronger assumptions buy speed, with adoption work

**Approach and reach.** Public by **2021**, formally described in **2022/2023**, and still included in CinderX. An **AOT type/bytecode compiler feeds the method JIT**; specialized calls, slots, and unboxed primitive types reduce dispatch and allocation. Dynamic Python modules interoperate, but static modules/types gain restrictions such as immutability and automatic slots. It is a stricter Python dialect inside CPython, not a transparent replacement. The C API and NumPy come from its CPython host; independent NumPy-suite evidence is **unverified**. [Static Python semantics](https://facebookincubator.github.io/cinderx/static-python), [current tutorial/limitations](https://facebookincubator.github.io/cinderx/static-python/tutorial).

**Numbers and people.** The paper reports **3.7% more requests/s at maximum CPU load** after incremental Instagram migrations, plus microbenchmarks. A pyperformance summary is **unverified**. Its acknowledgments name the same **15 combined developers** as Cinder's, not a separately staffed team; separate FTE and exact inception date are **unverified**. The paper also found serious implementation soundness bugs. [Paper](https://arxiv.org/abs/2206.13831).

**Outcome.** Active. Gradual adoption and explicit static assumptions worked in a controlled large application. The tutorial still warns about rough edges and possible crashes. For Lucifer, static assumptions may be speculative JIT optimizations with correct fallback, but cannot silently become new restrictions on ordinary Python.

## Unladen Swallow: an early compatibility-first LLVM JIT without enough customers

**Approach and reach.** A **2009–early-2010** CPython 2.6.4 fork using LLVM function compilation, feedback, guards, and interpreter fallback; it retained the GIL and required C-source compatibility. PEP 3146 lists **15 public applications/libraries** used in compatibility testing, including NumPy, Django, Twisted, SQLAlchemy, SWIG, and ZODB. Tests failing the baseline or depending on bytecode internals were disabled, so “NumPy tested” does not mean Lucifer's exact suite bar. Three PEP authors—**Collin Winter, Jeffrey Yasskin, Reid Kleckner**—are verified principals; paid FTE is **unverified**. [PEP 3146](https://peps.python.org/pep-3146/).

**Numbers.** Its historical **`perf.py`**, an ancestor of later suites, is not modern pyperformance. Revision r988 against CPython 2.6.4 on x64 Opteron 8214 HE/GCC 4.2.4 gave **1.30× Django**, **2.86× nbody**, and **1.08× slower rietveld**. It missed the 5× objective; normal startup was **1.60× slower**, with workload maximum-memory ratios **1.11–7.92×**. These are PEP measurements, not a new summary.

**Why it stopped.** Kleckner's **2011 retrospective** identifies insufficient Google customers: deployment changes were hard even for a CPython-2.6-based substitute, and prospective users chose other solutions. Staff availability and academic incentives faded; upstream expected Google maintenance that would not exist. LLVM compilation/memory costs were substantial, and Python optimizations still required custom feedback and alias analysis around runtime calls. These are observations about that implementation and period's LLVM, not a verdict on current LLVM. Its benchmark work outlived the runtime. [Original retrospective](https://qinsb.blogspot.com/2011/03/unladen-swallow-retrospective.html).

## Jython: JVM integration and parallel threads, without the C ecosystem

**Approach and reach.** Java implementation compiling Python to **JVM bytecode**, optimized by the host JVM JIT, with managed GC and real JVM threads. Its Java embedding/library ecosystem is a substantial success distinct from CPython acceleration. JPython began in **late 1997** under Jim Hugunin; Barry Warsaw and then Finn Bock led subsequent phases. Current releases still implement **Python 2**, while Python 3 remains development work. Exact historical/current FTE is **unverified**. [Official history](https://www.jython.org/jython-old-sites/archive/22/history.html), [current project](https://www.jython.org/).

**C API / NumPy / speed.** Ordinary CPython C extensions are unsupported; a maintainer explicitly confirms NumPy cannot install for this reason. **JyNI** is a separate bridge effort, not verified full modern NumPy support. Pure-Python packages compatible with the language version and Java libraries are the viable ecosystem. No primary pyperformance summary or complete NumPy-suite result was verified. [Maintainer's NumPy response](https://bugs.jython.org/issue2928).

**What stalled.** The Python-3 roadmap documents costly architectural reorganization, strings/I/O changes, and platform bugs. A previous Python-3 branch became unsuitable because it had not incorporated continuing trunk fixes. The roadmap intentionally supplies no delivery date. This is version-transition and maintenance debt, not total abandonment, and it shows that eliminating the GIL via a managed runtime does not deliver CPython's native packages. [Primary roadmap](https://www.jython.org/jython-3-roadmap).

## IronPython: CLR integration survived its original sponsor

**Approach and reach.** DLR/CLR code generation and the .NET JIT, managed objects/GC, and .NET threading/library interoperability. Jim Hugunin publicly presented it in **2004**; his 2005 conference abstract dates the first public release to OSCON 2004. This contemporary evidence overrides a later history page's conflicting creation date. Microsoft handed community leadership to **Jeff Hardy in October 2010**; Alex Earl and Benedict Eggers later describe its revival. Exact concurrent/current staffing is **unverified**. [Hugunin's conference abstract](https://www.jaoo.dk/jaoo2005/speakers/show_speaker.jsp?oid=63), [sponsorship history](https://ironpython-test.readthedocs.io/en/latest/license.html), [maintainers' interview](https://talkpython.fm/episodes/show/74/past-present-and-future-of-ironpython).

**C API / NumPy / speed.** It does not generally load CPython C extensions. **Ironclad** tried to bridge that gap: its README calls the original project inactive and describes a revival targeting IronPython/CPython 3.4; it explicitly says **NumPy still fails to import**. Historical ports are not modern unchanged NumPy support. No pyperformance summary was verified. [Ironclad status](https://github.com/IronLanguages/ironclad).

**Outcome.** Microsoft sponsorship ended, but the runtime survived. IronPython 3 still targets **Python 3.4**; **3.4.2 was released in December 2024**. The language-version lag and missing native ecosystem are verified limitations. A definitive primary explanation for Microsoft's withdrawal is **unverified**; do not turn sponsor departure into an invented technical post-mortem. [Current README](https://github.com/IronLanguages/ironpython3), [release](https://github.com/IronLanguages/ironpython3/releases/tag/v3.4.2).

## Pyjion: reuse CPython objects and another runtime's code generator

**Approach and reach.** A **function/frame JIT** translates Python bytecode into ECMA CIL and uses .NET **RyuJIT** to emit native code. Unlike IronPython, CPython still supplies Python objects, native extensions, and the runtime. Brett Cannon and Dino Viehland led the **2016** experiment; Anthony Shaw led the **2020–2022** rewrite. These establish named principals, not simultaneous FTE. The rewrite removed original patched-runtime/Windows deployment obstacles. [Shaw's architecture/history](https://tonybaloney.github.io/posts/running-python-on-dotnet-5-with-pyjion.html).

**Compatibility and numbers.** Keeping the host CPython loader supports normal C extensions architecturally, but a full enabled-JIT NumPy-suite result is **unverified**. Documentation lists unsupported compilation paths, including `with` and async/await; a historical statement that the original version passed CPython tests must not be applied automatically to the rewrite. No reliable full pyperformance summary was found; development docs say some suite tests remain incompatible. [Limitations](https://pyjion.readthedocs.io/en/latest/limitations.html), [benchmark documentation](https://pyjion.readthedocs.io/en/latest/development.html).

**Stall.** Latest release **2.0.0, November 2022**, targets .NET 7; current instructions still require CPython **3.10**. In 2024 Shaw said CPython's own JIT made Pyjion less necessary. A fuller abandonment/funding post-mortem is **unverified**. Version coupling and distribution complexity are documented burdens, not proof of a particular funding decision. [Release](https://github.com/tonybaloney/Pyjion/releases/tag/2.0.0), [README](https://github.com/tonybaloney/Pyjion), [Shaw's later assessment](https://tonybaloney.github.io/posts/embedding-python-in-dot-net-with-csnakes.html).

## Psyco: effective specialization trapped in a narrow backend

**Approach and reach.** A CPython extension specializing blocks into multiple **runtime-generated machine-code versions**, with virtual objects and value/type knowledge. It is neither meta-tracing nor an independent Python interpreter. Its hand-written backend supported **32-bit x86 only**; CPython handled unsupported operations and native extensions. NumPy's compiled kernels would remain external; an actual complete NumPy-suite result is **unverified**. [Technical introduction](https://psyco.sourceforge.net/introduction.html).

**Numbers, people, dates.** Rigo publicly announced the proof of concept on **2001-06-22**. No pyperformance result was verified. The homepage's historical **“typically 4×”** claim lacks a specified comparable suite. Armin Rigo moved his main effort to PyPy around **2005**; Christian Tismer revived Psyco v2 in **2009**, with Raymond Hettinger also credited by the PSF in **2010**. Exact concurrent staffing is **unverified**. [Original announcement](https://mail.python.org/pipermail/python-dev/2001-June/015503.html), [Tismer's announcement](https://lwn.net/Articles/341953/), [PSF award record](https://pyfound.blogspot.com/2010/07/).

**What ended it.** The project notices record missing 64-bit support in 2009, an incomplete Python-2.7 port in 2010, and declare it **unmaintained and dead on 2012-03-12**, directing users to PyPy. The introduction explains that PyPy offered more freedom to experiment and less synchronization with CPython. This is concentrated expertise plus architecture/version maintenance, not inability to call the C API. [Dated primary notices](https://psyco.sourceforge.net/).

## Faster CPython: specialization succeeded; the JIT hit an institutional limit

**Approach and years.** Mark Shannon's performance plan preceded the Microsoft-backed **2021** effort; Microsoft's 2022 profile describes **six engineers**. **PEP 659** added adaptive specialization and inline caches: a faster interpreter, not itself a native JIT. Python **3.11** officially reports **1.25× average speed versus 3.10** on the standard benchmark suite, with 10–60% individual improvements. This is an overall release result, not a measurement attributable solely to specialization. [Team profile](https://devblogs.microsoft.com/python/python-311-faster-cpython-team/), [PEP 659](https://peps.python.org/pep-0659/), [3.11 performance report](https://docs.python.org/3.11/whatsnew/3.11.html#faster-cpython).

**Copy-and-patch.** The experimental **3.13** JIT lowered specialized bytecode to micro-op traces, optimized them, and assembled precompiled native templates with patched operands. LLVM generates stencils **at build time**; it is not invoked as a heavyweight runtime optimizing compiler. Initial performance was approximately interpreter parity. CPython retains its C API/native ecosystem rather than emulating a second object model; a release-specific entire NumPy suite under enabled JIT is **unverified** here. [PEP 744](https://peps.python.org/pep-0744/).

**Measured later speed.** The subsequently withdrawn **PEP 836** reports **4–12% pyperformance geometric-mean uplift** for the **3.15 JIT versus its corresponding interpreter**, measured across Tier-1 platforms during **2026-06-16–27**. It proposed method-based compilation and first-class free-threading support as future work; those proposals are not delivered features. Its three authors identify proposal leadership, not total team staffing. [PEP 836 and measurement appendix](https://peps.python.org/pep-0836/).

**What actually stalled in 2026.** On **June 5**, the Steering Council froze new JIT functionality on main pending an accepted standards PEP covering maintenance, architecture, compatibility/free-threading, tooling, security, distribution, and measurable goals. It allowed six months before a removal path. On **October 19**, the authors withdrew PEP 836 because they lacked the personal bandwidth to carry the proposal forward. As of this report's date: new development halted and the graduation proposal withdrawn; deletion from main is **unverified**. Released experimental JITs and the specializing interpreter must not be described as abandoned together. [Council's explanation](https://discuss.python.org/t/an-announcement-from-the-steering-council-regarding-the-jit-project/107638), [authors' withdrawal](https://discuss.python.org/t/pep-836-jit-go-brrr-the-path-to-a-supported-jit-compiler-for-cpython/108010/57).

## The nogil fork: a fork that stopped because its central idea went upstream

**Approach.** Sam Gross's public **2021** CPython-3.9 fork was a **parallel interpreter**, not a JIT. Upstream PEP 703 combines biased/deferred reference counting, immortal objects, container locks, GC changes, and allocator-assisted optimistic access. Gross is a verified principal implementer; exact original team FTE is **unverified**. [Original announcement](https://mail.python.org/archives/list/python-dev%40python.org/thread/ABR2L6BENNA6UPSPKV474HCS4LWT26GY/), [PEP 703](https://peps.python.org/pep-0703/).

**C API / NumPy.** Existing extensions needed rebuilding and sometimes source adjustments; the no-GIL ABI is distinct. Borrowed references and unsynchronized direct field accesses require particular care. Upstream CPython can re-enable the GIL when an extension does not declare support; that escape is incompatible with Lucifer's fixed no-GIL bar. NumPy's own docs date experimental support to **NumPy 2.1 / CPython 3.13**, with warnings about shared mutation and object-dtype races. A passing suite and race-safe extension behavior are separate evidence obligations. Sources: `vendor/cpython/Doc/howto/free-threading-extensions.rst`; `vendor/numpy/doc/source/reference/thread_safety.rst:103–120`; [public NumPy docs](https://numpy.org/devdocs/reference/thread_safety.html).

**pyperformance.** PEP 703 reports pyperformance **1.0.6** overhead against an **immortal-object-enhanced 3.12 baseline, commit `018be4c`**, not an untouched release: **6% Skylake / 5% Zen3 single-thread**, **8% / 7% with multiple threads**. These mean additional elapsed time, not multicore speedups. They cannot establish a universal 5–6% cost for future builds. [Measurement section](https://peps.python.org/pep-0703/#performance).

**Outcome and years.** The fork was archived in **May 2025** because PEP 703 was accepted and work moved into **CPython 3.13+**. Free-threading became supported, still optional, in **3.14**. This is successful upstream transition, not abandonment of no-GIL Python. Lucifer inherits direct evidence that parallel CPython semantics are feasible, and equally direct evidence that native extensions require an explicit concurrency contract. [Fork status](https://github.com/colesbury/nogil), [PEP 779](https://peps.python.org/pep-0779/).

## Nuitka: compatible AOT compilation and deployment, not a replacement object model

**Approach and reach.** Python → C → native **AOT compilation**, linked to **libpython**. It preserves CPython objects and runtime operations, and therefore much of the native ecosystem. NumPy/SciPy and other extension packages are supported, although standalone distribution still needs package-specific shared-library, data, and import rules. An independent complete NumPy-suite certification is **unverified**. [Architecture](https://nuitka.net/pages/overview.html), [package/deployment issues](https://nuitka.net/user-documentation/common-issue-solutions.html).

**Numbers and people.** No complete primary pyperformance comparison was verified. Its performance page gives **3.353× Pystone with LTO**, **3.663× with PGO**, against Debian Python **2.7**, selecting fast runs of one synthetic test. These are not modern whole-application measurements. Kay Hayen's introduction establishes public work since **August 2010** and one founder; current paid team size is **unverified**. [Performance page](https://ftp.nuitka.net/user-documentation/performance.html), [founder's introduction](https://nuitka.net/posts/starting-to-blog-who-and-why.html).

**Outcome.** Active, not abandoned. Reusing CPython makes compatibility and native packaging achievable, while object-operation costs remain unless analysis can remove them. The project's continuing type-inference work makes clear that native code output alone does not mean native scalar performance. For Lucifer, retaining the C-facing contract need not require retaining every CPython execution cost, but eliminating those costs needs actual proofs/guards.

## Codon: large numerical gains by choosing a different compatibility contract

**Approach and reach.** **LLVM AOT**, static bidirectional typing, monomorphization, a domain-oriented IR, and native parallelism; it also exposes a function-JIT decorator and CPython extension output. It intentionally restricts/changes Python semantics. Existing libraries can run through an embedded **CPython bridge**; native NumPy support is a **reimplementation**, not an unchanged NumPy native build executing on Codon's own full C API. [FAQ](https://docs.exaloop.io/start/faq/), [implementation/current NumPy support](https://github.com/exaloop/codon).

**Measured subset.** CC '23 Appendix B, **Codon 0.15**, M1 Max/macOS 12.5.1, reports selected pyperformance-derived tests below. Speedups are simple divisions of the paper's times. The paper names CPython 3.10.8 and 3.8.2 across its experiments, but this table labels its baseline only “Python”; its exact baseline association is **unverified**. The harness was adapted, and this is **not a full pyperformance run or summary**. [Primary paper](https://commit.csail.mit.edu/papers/2023/cc_Codon.pdf), [accessible copy](https://regmedia.co.uk/2023/03/11/mit_codon_paper.pdf), [benchmark adaptation notes](https://github.com/exaloop/codon/blob/develop/bench/README.md).

## Mojo: an active systems language, with CPython interoperability

**Approach and reach.** Python-inspired **MLIR/native compilation** with explicit types, ownership, compile-time computation, and CPU/GPU facilities. Python libraries, including NumPy, are accessed by loading **unmodified CPython**; reverse bindings expose selected Mojo functions/types as extensions. This inherits access through CPython, rather than demonstrating Mojo's own implementation of the full C API or NumPy suite. Current interoperability docs list **Python 3.10–3.14**. [Python interoperability](https://mojolang.static.modular.com/1.1.0/docs/manual/python/).

**Numbers and people.** No unchanged-source full pyperformance result was verified; typed kernel rewrites answer a different question. Publicly launched **2023-05-02**. Creator Chris Lattner, lead Tatiana Shpeisman, and engineer Jeff Niu are documented participants, not a complete staffing count; Mojo-only FTE is **unverified**. [Launch](https://www.modular.com/blog/a-unified-extensible-platform-to-superpower-your-ai), [2023 engineering speakers](https://www.modular.com/blog/modcon-2023-sessions-you-dont-want-to-miss).

**What changed.** The language remains active: **Mojo 1.0 was fully open-sourced on 2026-08-18**. Its current roadmap prioritizes systems/accelerator programming and explicitly says it **may or may not become a full superset of Python**. That is a deliberate change in the compatibility proposition, not evidence that fast unchanged Python has been achieved or that Mojo has died. [Official announcement](https://www.modular.com/blog/modcon-announcements), [1.1 roadmap](https://mojolang.org/1.1.0/docs/roadmap/).

## RustPython: independent implementation first, optimization and C API incomplete

**Approach and reach.** A Rust **bytecode interpreter and independent object system**, useful for embedding and WebAssembly. The optional function JIT remains explicitly experimental; documentation demonstrates manual `__jit__()` rather than a production optimizing tier. The public repository dates to **2018-05-28**; Windel Bouwman and Shing Lyu presented it at FOSDEM 2019. Exact team FTE is **unverified**. [README](https://github.com/RustPython/RustPython), [repository chronology](https://api.github.com/repos/RustPython/RustPython), [firsthand presentation](https://archive.fosdem.org/2019/schedule/event/rust_python/).

**C API / NumPy.** A blanket “no C API” is now outdated: **rustpython-capi 0.6.0, October 2026**, describes **minimal compatibility exports**. That is not full non-limited compatibility. NumPy/pandas support requests remain unresolved evidence; no unchanged NumPy-suite pass was verified. A 2026 maintainer discussion identifies static built-in type symbols and allocation-prefix/layout assumptions as concrete compatibility obstacles. [C-API crate](https://docs.rs/crate/rustpython-capi/0.6.0), [NumPy issue](https://github.com/RustPython/RustPython/issues/1464), [2026 request](https://github.com/RustPython/RustPython/issues/7398), [layout discussion](https://discuss.python.org/t/c-api-add-py-getbuildintype-and-py-getbuildintypeborrowed/107010).

**Performance and outcome.** Current benchmarks adapt some **pyperformance 1.14.0** tests, remove its harness/timers, sometimes shrink inputs, and use Criterion/CodSpeed, with compilation/fresh namespaces included. A standard full-suite summary is **unverified**; the project's benchmark page must not be relabeled one. Active, with production-readiness limitations acknowledged; no abandonment post-mortem exists in the sources reviewed. [Results](https://rustpython.github.io/benchmarks), [methodology](https://github.com/RustPython/RustPython/blob/main/benches/README.md).

## SPy: high-level built-ins, purchased with frozen semantics

**Approach.** An interpreter plus **AOT compiler for a static Python variant**. “Blue” computation happens during partial evaluation/redshifting; “red” operations remain at runtime, then compile through C to native/WASM targets. Imports and the resulting program world can be frozen for static dispatch. This is an informative way to implement a language in itself, not unchanged full Python. [Project](https://github.com/spylang/spy), [creator's design account](https://antocuni.eu/2025/10/29/inside-spy-part-1-motivations-and-goals/).

**C API / NumPy.** Current CFFI extensions offer partial interoperability; a fuller CPython mode using `Python.h`, libpython, and shared reference counting remains roadmap work. Passing a buffer to a compiled function is not executing upstream NumPy's suite on an independent runtime. Cuni's design account describes **list and dict implementations in SPy**; the roadmap records their library files and many incomplete semantics/stdlib features. [Design account](https://antocuni.eu/2025/10/29/inside-spy-part-1-motivations-and-goals/), [roadmap, updated April 2026](https://github.com/spylang/spy/blob/main/ROADMAP.md).

**Numbers, people, outcome.** Repository created **2023-05-19**. Antonio Cuni's October 2025 account thanks Anaconda for **100% of his time**: at least one funded full-time developer then, not verified total staffing. It reports a **200× raytracing demo** while explicitly saying the implementation is usable only for demos at that date; no pyperformance result was verified. Active thereafter, not abandoned. It gets predictable compilation by deliberately rejecting some Python behaviors. Lucifer can learn from the high-level built-ins without treating SPy's restrictions as compatible semantics. [Funding/demo account](https://antocuni.eu/2025/10/29/inside-spy-part-1-motivations-and-goals/), [repository chronology](https://api.github.com/repos/spylang/spy).

## LPython: retargetable numerical compiler, apparently quiet

**Approach and reach.** Typed numerical **AOT and decorator JIT**, using the Abstract Semantic Representation shared with LFortran and LLVM/C/C++/WASM backends. Typed arrays are supported; `@pythoncall` and `--link-numpy` invoke CPython libraries, leaving those calls at CPython's execution model. This is not full C-API compatibility in an independent runtime or an unchanged NumPy-suite demonstration. [Architecture/interop announcement](https://lpython.org/blog/2023/07/lpython-novel-fast-retargetable-python-compiler/).

**Numbers and people.** No full pyperformance result was verified. Published numerical examples use typed source and sometimes `--fast`/fast-math; they cannot be substituted for unchanged Python. Public repository created **2021-12-29**; the 2023 announcement has **13 named authors**, led by Ondřej Čertík. A read-only API count returned **70 lifetime contributor accounts**, potentially including shared/inherited work, not 70 current staff. Exact paid FTE is **unverified**. [Repository metadata](https://api.github.com/repos/lcompilers/lpython), [contributors](https://api.github.com/repos/lcompilers/lpython/contributors?per_page=100).

**Stall evidence and uncertainty.** The website's alpha/heavy-development language must be weighed against the latest compiler release, **v0.22.0 on 2024-07-08**, and latest observed default-branch commit, **2025-12-11**, as checked for this report. The repository is not archived. A primary explanation for the quiet period—funding, reprioritization, or otherwise—is **unverified** after searching project announcements/history. Do not invent one. [Compiler release](https://github.com/lcompilers/lpython/releases/tag/v0.22.0), [last observed commit](https://github.com/lcompilers/lpython/commit/6b00cbaa6621e63535030fe88d181f1208113400).

## What this survey does and does not establish

The strongest verified pyperformance evidence here is Pyston v2's dated release comparison, CPython's dated release/JIT results, the nogil proposal's explicitly qualified overhead measurements, and GraalPy's less fully specified maintainer headline. Codon's adapted tests and RustPython's re-harnessed tests are separately identified. Most historical projects do **not** have a verified modern full-suite figure in the reviewed material; inventing one would make the comparison worse. Searches/readings used project READMEs, official docs, papers, release notes, and authors' retrospectives; missing evidence is not a claim that no such measurement has ever existed.

Likewise, no reviewed source demonstrates Lucifer's **whole conjunction**: independent fast runtime, full non-limited C API with the stipulated unmodified NumPy build/suite, no GIL, and predominantly Python built-ins. PyPy's NumPy result, Pyston's near-complete historical result, upstream free-threaded NumPy, and SPy's self-hosted built-in direction establish different pieces. This is an evidence gap, not a proof of impossibility. Exact present FTE counts and several cessation causes remain **unverified** despite examining the sources listed above; maintainer absence, stale releases, and archived forks do not identify a cause on their own.

The transfer from the Smalltalk VM must also be stated narrowly. Its `README.md` at `origin/master` documents a freestanding assembly VM, high-level library/application policy, M:N processes, native compilation, and bounded language/production readiness. The owner's AWFY ratios are supplied context; **their underlying runs were not independently audited in this task** and do not predict Python performance. CPython object/layout, native-extension, and concurrency obligations come from a different corpus: the local CPython headers, free-threading extension guide, NumPy threading docs, and PyPy cpyext evidence above.

## What Lucifer must get right first

The following are **design recommendations inferred from the source evidence**, not claims that Lucifer already implements them. They order uncertainty reduction; they do not postpone any fixed requirement or propose a limited-API/GIL/subset fallback as the public product.

1. **Make one coherent contract for C-visible objects, Python built-ins, and parallel access.** Specify stable exposed identities/addresses, layouts and exported type objects, ownership/borrowed references, finalization, buffer lifetimes, extension-defined allocation, and reentrant callbacks. If optimized Python storage differs from C-visible storage, define exactly who owns authoritative state, when materialization occurs, how C writes become visible, and how JIT assumptions are invalidated. A full C API implemented as callable functions alone is insufficient when macros read/write fields directly. 2. **Specify production no-GIL semantics and their native boundary together.** Cover mutation/iteration, borrowed references, object and allocator locking, refcounts/GC, finalizers, exceptions, callback reentrancy, and lock ordering. This task performs none of those executions; the acceptance result remains **unverified**.

4. **Prove that predominantly Python built-ins remain efficient across those boundaries.** Define a small native primitive set for raw storage/atomicity, allocation/GC, foreign calls, and indispensable machine operations; implement algorithms and semantic policy in Python as required.
